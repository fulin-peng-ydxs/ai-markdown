# Plainroot 页面开发流程（AI 固定流程）

> 本文负责把“页面交给 AI 开发”变成可检查的闭环。视觉事实源是根目录 `DESIGN.md`，产品事实源是同目录 `requirement.md`，仓库协作红线见根目录 `AGENTS.md`。

## 0. 适用边界

以下改动必须执行本流程：

- 新增或改造窗口、页面、工作台区域、页签、弹窗、菜单、抽屉、设置模块；
- 修改布局、样式、主题 token、响应式、滚动、键盘、焦点或真实点击链路；
- 新增可复用 UI 组件、前端状态模型、桌面桥接交互或页面级持久化偏好。

纯 Rust 内部实现、无界面影响的工具函数或只改文案时，可在计划中写明“不触发页面开发闭环”，但仍需验证受影响行为。

## 1. 开工前必读

1. 根目录 `AGENTS.md`。
2. `requirement.md` 中对应需求编号、页面功能点、异常与验收。
3. 当前阶段 `plan.md`，确认本次只实现阶段内能力。
4. 根目录 `DESIGN.md` 的 §1～§8。
5. 对应 HTML 原型；只提取结构、状态和视觉，不复制固定路径、假数据、计时器或原型说明。
6. 工程建立后，再读取同类页面、组件、hook、desktop service、Rust command 和测试。

## 2. 固定流程

1. **定位**：写清页面职责、入口、用户主任务、需求编号、当前阶段覆盖和明确不做项。
2. **核对原型**：标出保留区域、当前阶段隐藏/禁用区域，以及原型无法表达的系统能力。
3. **梳理状态**：至少覆盖 ready、loading、empty、error；按页面补 readonly、dirty、saving、conflict、missing、permission-denied、partial-success 或 draft。
4. **确定提交边界**：写清数据来自 Markdown、Rust 命令、版本化 Store 还是窗口内存；UI 何时可更新、失败如何回滚、内容是否仍安全。
5. **复用检查**：全局查同类组件、状态 reducer、hook、desktop adapter 和 Rust command。职责相同的第二处实现优先复用或抽取。
6. **形成页面设计块**：把第 3 节模板填入开发计划。存在多种合理布局、交互、文件语义或平台方案时，先给用户推荐和理由。
7. **实现**：先接真实状态和错误，再做视觉细节；不进入当前阶段的控件不绑定空操作，也不用 mock 伪装完成。
8. **维护闭环**：按第 5 节同步真实组件、状态契约、token、桌面桥接、页面消费和测试。
9. **验证**：执行实际清单中已存在且已验证的静态检查、测试、构建和 E2E；再做关键窗口尺寸与平台能力复核。
10. **登记事实**：代码与计划候选不一致时更新文档；新增稳定视觉或交互规则时同步 `DESIGN.md`。

## 4. 页面原型选型

| 类型 | 使用场景 | 稳定结构 | 不应出现 |
|---|---|---|---|
| `launcher` | 无工作区、首次启动、最近目录与恢复 | 打开本地内容主入口 + 最近工作区辅助列表 | 营销 hero、统计卡、虚假编辑器 |
| `workbench` | 文档编辑、阅读、页签、文件树和大纲 | 稳定 chrome + 中央文档主区 + 可退化辅助区 | 通用后台导航、卡片仪表盘、多主滚动 |
| `settings-studio` | 主题等需要编辑、验证和预览的复杂设置 | 上下文导航 + 对象列表 + 编辑区 + 预览 + 固定提交 | 保存即实时污染全局、无预览的颜色表单 |
| `dialog` | 确认、少字段输入、冲突与关闭保护 | 明确对象、后果、操作动词和安全边界 | 长流程、宽表、含糊“确定”、依赖原生 `confirm()` |

不为单个页面创建新的“原型名”。只有现有四类无法表达稳定且会重复出现的结构时，才提出新原型，并先确认其必要性。

## 5. 组件与能力维护矩阵

正式工程建立后，按变更类型同步以下事实；实际文件路径以工程为准，不在脚手架前伪造注册文件。

| 变更类型 | 必须同步维护 | 必须验证 |
|---|---|---|
| 新页面/窗口 | 入口、需求映射、页面状态、同类复用、阶段计划 | 组件测试、构建、关键窗口尺寸、真实主流程 |
| 窗口壳/菜单 | 平台适配、命令启用状态、标题来源、快捷键 | macOS 冒烟、Windows CI/人工清单、禁用项无空操作 |
| 对话框/菜单/抽屉 | 公共组件、焦点契约、Esc/遮罩/返回触发点、破坏性文案 | 键盘遍历、焦点圈定与恢复、取消/失败不改状态 |
| 文件树/最近列表 | 领域状态、Rust command、错误码、页面消费 | 临时目录集成、空/错/只读/失效、磁盘成功后刷新 |
| 页签/编辑器/大纲 | 单一活动页签来源、内容模型、锚点与独立会话 | 状态机、无损往返、关闭保护、恢复与外部冲突 |
| 主题 token/预设 | 运行时 token、`DESIGN.md`、主题 schema、真实消费 | 对比度、明暗隔离、草稿回退、保存广播、视觉回归 |
| 新复用组件/hook | 组件或 hook、职责说明、至少一个真实消费点 | 组件测试、消费页验证；无消费的空抽象不合入 |
| 新桌面 command | Rust 权限与路径校验、TypeScript adapter、稳定错误码 | Rust 单元/集成、前端失败态、跨平台差异 |

原则：新增“可配置能力”必须同时存在定义、持久化/校验和真实消费；页面没有读取的假配置、没有消费点的抽象组件和没有错误承接的 command 都不算闭环。

## 6. 状态与交互红线

- 磁盘操作成功前不得乐观改写正式文件树、页签路径或保存状态；需要即时反馈时使用明确的 processing 状态。
- 保存失败、只读、外部冲突、权限撤销和路径失效必须说明内容是否仍安全，并提供可行下一步。
- 活动页签变化必须原子驱动文档、文件树、大纲、状态栏和窗口标题，禁止各区域维护互相漂移的当前文件。
- 未实现能力必须隐藏或禁用并说明；禁用控件不绑定 toast 假反馈。
- Dialog 只承载确认和短任务；复杂设置使用 `settings-studio`，文档主流程留在 `workbench`。
- 同一操作组最多一个主按钮；危险操作使用具体结果动词，并与取消保持清楚距离。
- Toast 不替代错误面板、进度、对话框或持久状态。
- 所有图标按钮有可读名称和 tooltip；焦点顺序与视觉顺序一致，关闭浮层后回到触发点。
- 视觉状态不能只靠颜色；系统减少动态效果时关闭非必要 transition 和滚动动画。

## 7. 验证门禁

- 当前工程清单和验证基线已经建立；页面任务应从 `package.json`、`src-tauri/Cargo.toml`、仓库脚本、`README.md` 与 CI 配置选择适用命令，不能沿用过期计划中的候选命令或把未执行命令写成通过。
- 页面改动最低需要：代码自审、类型/静态检查、相关单元或组件测试、生产构建、真实点击链路 E2E、关键窗口尺寸检查。
- 文件或桌面能力还需：Rust 单元/集成测试、临时目录故障注入，以及 macOS/Windows 对应证据；浏览器 mock 不能替代最终原生验收。
- 关键窗口至少覆盖完整桌面、约 `1050px`、约 `820px` 和页面专属临界宽度；检查主任务、文本溢出、滚动归属、浮层边界、键盘与焦点。
- 只停止本次验证启动的进程，只操作临时工作区；不得为了测试触碰用户真实 Markdown、最近记录或系统配置。
- 任何必验命令失败时记录最短错误与影响，不把失败项写成已验证，也不连续猜命令变体。

## 8. 交付自检

- 需求编号、当前阶段和页面功能点是否一一对应？
- 原型中的假数据、固定路径、计时器和原型说明是否已排除？
- ready/loading/empty/error 及页面特有异常是否有真实数据来源和恢复路径？
- 文件、Store、页签和主题草稿的提交边界是否明确，失败是否保留安全状态？
- 是否优先复用同类能力，并同步了第二消费点和测试？
- 是否消费 `DESIGN.md` token，且没有新增私有颜色、间距、滚动或浮层体系？
- 窄窗口、键盘、焦点、非颜色反馈和 reduced-motion 是否验证？
- 构建、测试、E2E 和平台证据是否真实执行，未覆盖项是否明确说明？
- 稳定事实变化后，`AGENTS.md`、`DESIGN.md` 和本流程是否仍与代码一致？
